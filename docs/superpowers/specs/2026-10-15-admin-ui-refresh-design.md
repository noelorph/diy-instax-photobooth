# Cohesive Admin UI refresh

**Status:** Implemented and verified against the isolated local stack following the owner's approved Admin UI direction, shared Geist typography, and `src/components/` location. Hosted staging verification and promotion remain pending until a separate staging project is identified.

## Intent and scope

Give the existing Admin experience a distinct, cohesive interface while following [DESIGN_SYSTEM.md](../../../DESIGN_SYSTEM.md). The reference is the [CodeRabbit app's publicly visible navigation and settings layout](https://www.coderabbit.ai/blog/how-to-deploy-and-integrate-mcp-servers-with-coderabbit): persistent navigation, clear page actions, compact information density, and precise control detail. Adapt those patterns to this photo booth's identity and existing semantic tokens. Do not reproduce CodeRabbit branding, orange accent, content, or page structure where it does not fit this product.

Apply the refresh to every Admin screen currently implemented: `/sign-in`, `/forgot-password`, `/reset-password`, the authenticated AppShell, `/dashboard`, `/events`, `/events/new`, `/events/[eventId]`, `/history`, and `/profile`, including their loading, empty, error, pending, and success states. Dashboard and History remain protected foundation pages. This is a presentation and component-ownership change; the [Admin access](2026-10-13-admin-access-and-shell-design.md) and [Draft Event](2026-10-13-draft-event-management-design.md) behavior, authorization, validation, and development gates remain in force. No Booth Mode, printer, stock, Live Event, or invented dashboard data enters this work.

Success means the Admin can recognize one visual system across all these routes, use the same controls and feedback patterns, and scan compact information without losing readability or accessible targets.

## Visual direction

Use Geist Sans Variable across the Admin refresh and future Booth Mode, as decided in [ADR-0019](../../adr/0019-use-geist-typography-across-admin-and-booth.md), with the design system's light and dark semantic palettes. The light Admin uses ivory canvas, white surfaces, ink text, and restrained teal actions; the saved Profile preference selects the documented dark palette for authenticated pages. Ordinary public auth stays light. Use the reference's compact 14/18 px secondary text and 16/22 px body rhythm in Admin screens; preserve larger Booth instruction and countdown roles. Do not add a new palette, second display font, gradient, or decorative card grid.

The distinctive cue is one small portrait photo-frame mark at the navigation brand and public auth heading. It evokes a physical print without imitating a product logo or applying an effect to Guest photos. Keep the rest of the interface quiet: spacing, alignment, and useful borders establish hierarchy. Page titles are left aligned. Supporting text explains the current task; it does not become a decorative eyebrow on every page.

At wide widths (1024 CSS px and above), keep the documented 240 px sidebar and at most 1280 px content region. The brand sits above icon-and-label navigation; Profile remains last. The selected destination uses `primary-soft`, `primary` text, and a visible marker. The content header pairs the title with one primary action where the page has one. At medium widths (640–1023 px), the rail collapses without hiding the accessible destination names. At compact widths, a labeled menu exposes the same destinations and the page uses a 16 px inset. Escape closes the menu and restores focus to its trigger. Loading and error content stays within the same shell.

Admin density follows the existing 4 px spacing rhythm: about 8–16 px inside controls and rows, 24–32 px between form sections, 14 px secondary row text, and 16 px form/body text. Table rows are compact enough to compare Drafts while every interactive target remains at least 44 CSS px where touch is used. Do not truncate Event names, schedules, statuses, or error causes needed for action. At compact widths and 200% zoom, Event rows become labeled summaries with their link and Draft status intact.

Public auth remains a centered, single column no wider than 480 px, with the small photo-frame brand cue, a clear heading, fields, feedback, one primary action, and recovery/navigation links. The Draft editor uses labeled sections and a two-column field layout where space permits, becoming one column at compact widths. Profile keeps descriptions adjacent to settings on wide screens and stacks them on compact screens. Dashboard and History placeholders retain their truthful scope and gain the shared page hierarchy only.

## Component ownership and styling

Create the `src/components/` directory as the project-wide reusable layer:

| Location                 | Responsibility                                                                                                                                                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/components/ui/`     | Selectively installed shadcn/ui primitives, customized to semantic tokens and the design system's states: Button, Input, Label, Native Select, Badge, and Alert for current screens. Add another primitive only when an implemented screen uses it. |
| `src/components/shared/` | Small product-neutral compositions: labeled field with helper and inline error, form feedback, page header, status badge, and empty state. These combine primitives without owning feature rules.                                                   |
| `src/components/layout/` | Reusable public auth frame and authenticated Admin shell/navigation.                                                                                                                                                                                |
| `src/features/admin/`    | Sign-in, recovery, Profile, and Draft form state, validation, actions, and page-specific compositions.                                                                                                                                              |

Use the shadcn/ui CLI configuration and the ordinary `@/*` TypeScript path mapping to `src/*`, which resolves `@/components/*` to `src/components/*`. Configure `components.json` aliases for `@/components` and `@/components/ui`; verify both TypeScript and Next.js resolve them. Tailwind CSS 4 utilities map to the existing theme-scoped semantic CSS variables. Customize installed shadcn/ui code locally; the design system's palette, radius, focus, disabled, loading, and error rules override registry defaults. Remove broad selectors such as `.auth-form input` and `.auth-form button` as their responsibilities move into components. Keep global CSS for tokens, resets, and genuinely global behavior; keep page layout rules near their owning layouts or features.

Use Lucide outline icons selectively: 16 px in dense rows and 20 px in standard controls/navigation, with consistent stroke weight. Visible labels identify navigation and actions. Decorative icons are hidden from assistive technology; an icon-only control has an accessible name and a visible pointer tooltip. Buttons retain `primary`, `secondary`, `quiet`, and `destructive` treatments where used. Style navigation links as links; never nest a link inside a button. Native select and date-time inputs retain standard form submission, keyboard behavior, and browser support.

The shared field composition must accept native input props and React Hook Form registration without dropping `name`, `ref`, or event handlers. It associates the visible label, optional help, and current inline error with the input; `aria-invalid` reflects the current error. Keep existing form-level summaries and inline feedback; do not suppress a current error during migration. Editing a Draft field continues to clear stale validation feedback as implemented. Pending actions block duplicate submission and retain a readable action label or adjacent status. Saved and reset-success messages appear only after the existing actions confirm completion.

## Migration and verification

Implement in reviewable slices: (1) theme bridge, shared component configuration, and shared primitives; (2) auth frame/forms and Admin shell; (3) Events list and Draft editor; (4) Profile and protected foundation pages; (5) visual and accessibility polish. Keep the current route and server-action contracts throughout. Do not rewrite authorization or persistence for a visual migration.

Use TDD for component behavior and interaction changes: observe a relevant regression test fail before a behavior fix, then pass. Existing component, integration, and browser journeys must continue to pass. Add focused tests for shared field associations, button/link semantics, navigation state/focus, and any changed feedback behavior. Do not add tests that merely duplicate CSS values.

Verify compact, medium, and wide layouts; light and dark Admin themes; ordinary public auth; keyboard focus and menu operation; 200% browser zoom; long Event and Client text; Draft empty, overdue, invalid, conflict, pending, and saved states; and recovery/reset errors and success. Verify that Geist loads from the application origin, remains readable at 200% zoom, and renders tabular counts and times consistently in both themes. Inspect rendered screenshots for visual consistency and compare them with this spec. Run lint, type checking, formatting, the full applicable test suite, production build, and Playwright browser checks. Complete an independent code review of the whole UI change against this spec and [DESIGN_SYSTEM.md](../../../DESIGN_SYSTEM.md), resolve findings, then verify again before declaring completion.

## Boundaries and deferred work

This refresh does not change the product's light/dark preference behavior, domain copy, privacy rules, or Admin/Booth authorization boundary. It does not build future first-release components such as print controls, media upload, readiness, dialogs, or Booth Mode merely because the design system lists them. When those flows are implemented, they consume the same semantic tokens and shared primitives under `src/components/` where behavior matches. See [ADR-0020](../../adr/0020-place-shared-ui-components-under-src.md).
