## 1. Scope and operating model

One Admin, one booth iPad, one Instax Mini Link 3, at most one Live Event and one unresolved Print Attempt across the system. Booking/payment happen elsewhere. The Admin prepares the iPad once, then normally manages the Event from their signed-in phone. The iPad stays at `/booth` through recoverable faults and deliberate pauses, including iPad Guided Access. Equipment repair may require physical help; routine repair does not require Admin sign-in on the iPad.

Every booked Film Package and Additional Film Package provides **10 prints**. No editable Print Allowance, Additional Prints units, shared Film Stock inventory, Wasted Film correction, Client Redaction or past-Event deletion remains in the target product. There is no in-app Test Print, inspection requirement or test result record. Setup shows only: **“Always test the printer before starting Booth Mode.”** Independent testing happens outside Event print accounting.

The product records confirmed physical ejection, including an unusable image, as one print. A new capture/session is needed for another copy. Ordinary successful printing must complete automatically; Admin inspection is exceptional recovery only. See the [proof checklist](../../qualification/booth-recovery-proof-checklist.md) before enabling real printer-backed Booth Mode.

## 2. State and accounting

### Event lifecycle

| From                  | Action and guard                                                                                           | To                                   |
| --------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| Draft                 | Start Booth Mode; complete valid setup, positive booked capacity, no other Live Event                      | Live                                 |
| Draft                 | Cancel Event                                                                                               | Cancelled                            |
| Draft                 | Delete Draft; never started, no current run/attempt work; remove private media before reporting completion | Deleted; opaque audit reference only |
| Live                  | Finish Booth Mode                                                                                          | Live; its run finishes independently |
| Live                  | Complete Event; all runs Finished and all attempts terminal                                                | Completed                            |
| Live                  | Cancel Event; all runs Finished and all attempts terminal                                                  | Cancelled                            |
| Completed / Cancelled | Read history                                                                                               | Same terminal state                  |

Cancelled and Completed Events have no delete, redact, reopen, or booking-edit action. A Live Event cannot be deleted. An Event may have several runs, but only one unfinished run at a time. After Finish, starting another run is a new local setup/handoff while the Event is still Live; it does not reset package or print totals. Complete Event is a separate phone Admin action. Schedule does not automatically start or finish an Event.

### Booth run and readiness

Run states are `Prepared`, `Active`, `Paused`, `Finishing`, `Finished`. Temporary unavailability is a set of readiness blockers, not an Event state or an implicit Admin pause.

| Action                                             | State effect                                                       | Guest / print effect                                                                            |
| -------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Successful start transaction                       | Create Prepared run and inactive grant                             | No guest work before handoff activation                                                         |
| Confirm initial receipt after local Admin sign-out | Prepared → Active                                                  | Only initial handoff; recovery-purpose receipt activates the grant while run stays Paused       |
| Failed/abandoned handoff                           | Prepared → Paused; unusable grant revoked                          | Neutral setup-recovery sign-in; no automatic guest entry                                        |
| Pause Booth                                        | Active → Paused immediately                                        | Block new work; abandon unsent session; already dispatched attempt continues or remains pending |
| Resume Booth                                       | Paused → Active only after readiness passes and no pending attempt | Fresh welcome; authenticated Admin action required                                              |
| Equipment/network fault                            | State unchanged, blocker added                                     | Stop new work; apply section 4 recovery                                                         |
| Recovery                                           | Remove only the verified blocker                                   | Welcome only if Active, all blockers clear and no pending attempt                               |
| Finish Booth Mode                                  | Prepared / Active / Paused → Finishing                             | Stop new work; settle/cancel unsent work; wait for any possible print outcome                   |
| All attempts terminal                              | Finishing → Finished; revoke grant                                 | “Booth Mode finished” with Sign in                                                              |

A pending attempt prevents Resume and final Finish, but does not prevent recording a pause or finish request. Paused is a durable Admin choice; reconnect, reload confirmation, added packages and resolved outcomes never override it. A Finish request cannot be reversed by Resume. A new run requires an explicit Admin start after the previous run is Finished.

Readiness is evaluated at the operation's stage. **Equipment checks** mean reachable server, permission **and live camera feed**, connected qualified printer ready to accept a new job, loaded-film confirmation, Guided Access and printer-power confirmations, and the applicable hardware release policy. Optional media failure uses the default welcome and does not block operation. A printer count is diagnostic only, never physical inventory.

| Predicate                  | Checks at this stage                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setupReady`               | Current local Admin session; valid Draft or Live Event eligible for a new run; no competing Live Event/unfinished run/unresolved attempt; positive available booked prints; equipment checks from the setup device. No pre-existing run or device grant is required: start creates them.                                                                                                                                                                        |
| `guestReady`               | Active run and valid active device grant; equipment checks; positive available prints; no unresolved attempt or active Guest Session. Used to admit Start.                                                                                                                                                                                                                                                                                                      |
| `reserveReady`             | Active run/grant, matching current Guest Session and acknowledged explicitly selected Capture with no strictly newer shutter in that session (ties allowed); equipment checks; positive available prints and no unresolved attempt. Used to reserve exactly one unit.                                                                                                                                                                                           |
| `dispatchReady`            | Active run/grant, same current session and bound Capture with no strictly newer acknowledged shutter in that session (ties allowed), and **own Reserved attempt**; equipment checks for the current connection generation; no other unresolved attempt; its hold still valid and `Printed + unresolved ≤ total_booked_prints`. The own hold is allowed: **`prints_available = 0` is valid for dispatch of the last reserved unit**. No second unit is required. |
| Resume                     | Paused run, existing valid active grant, equipment checks, positive available prints and no unresolved attempt/active session. Transition to Active then show welcome; do not apply `guestReady`'s Active-state requirement before Resume.                                                                                                                                                                                                                      |
| Observation/reconciliation | Valid scoped authority and allowed attempt transition; do not require camera, available capacity or Active run. A Paused/Finishing run can settle old work.                                                                                                                                                                                                                                                                                                     |

Dynamic camera/connection/idle checks must have been observed and received by the server within the preceding **five seconds**, and must match the current connection generation; delayed reports outside that age cannot refresh readiness. The client rechecks live state immediately before its send. Poll/report every two seconds while visible, and refresh after focus/reconnect; missing/stale reports block new admission/dispatch/Resume. Use server receipt time plus validated observation age, never a future client timestamp as proof of freshness. First setup reports these checks under Admin authority; subsequent reports use the device grant.

Loaded-film, power and Guided Access confirmations are scoped to the run and physical equipment. An ordinary same-printer reconnect does not erase an existing load confirmation; it invalidates dynamic printer readiness until refreshed. A reliable no-film/cover-open/load-change observation or explicit Admin reload request invalidates the load confirmation and creates a new reload request; a different printer identity is rejected for the current run and requires a new explicit setup after the old run is safely Finished. Confirming the current request is bound to its current generation/revision, so an old button cannot clear a new fault. A new run requires fresh setup confirmations. These attestations are physical checks, not a claim that the app measured ten usable sheets.

### Print Attempt lifecycle

A Guest Session tracks interaction; a Print Attempt tracks a physical possibility. Ending the session or discarding its photo **does not resolve an attempt**.

| State       | Meaning and allowed next state                                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reserved    | Server holds one Event print and the single printer slot; no dispatch authorization yet. Cancel to NotPrinted if dispatch has not been authorized. |
| Dispatching | Server authorized the one send; command may reach the printer. May become Accepted, Printed, NotPrinted or Pending.                                |
| Accepted    | Command acknowledged; physical outcome still unresolved. May become Printed, NotPrinted or Pending.                                                |
| Pending     | Outcome cannot be established; retains hold and printer slot. Only reliable attempt-specific observation or inspected Admin resolution can end it. |
| Printed     | Terminal full-ejection outcome; one Confirmed Print.                                                                                               |
| NotPrinted  | Terminal reliable no-output outcome; release hold with no print counted.                                                                           |

Reserved, Dispatching, Accepted and Pending are all unresolved. A crash after dispatch authorization is conservative Pending even if the adapter might not actually have sent. A live adapter may report definitely-not-sent only when it can prove that no write began. An acknowledgement, elapsed time, printer counter change, reload, lost response or disconnected socket is never proof of Printed or NotPrinted.

Normal path: `Reserved → Dispatching → Accepted → Printed`; Accepted can be omitted if reliable completion arrives first. Reliable no-film rejection may end as NotPrinted only after #17 proves it refers to this attempt and no sheet ejected. Otherwise use Pending. A duplicate terminal observation returns the prior result. Conflicting later evidence never silently rewrites a terminal outcome: record a discrepancy for Admin review, block the affected run, and preserve both evidence records. No correction action refunds a confirmed print.

### Formulas and invariants

Let `B` be original booked packages, `A` the sum of Additional Film Packages, `C` Printed attempts and `U` unresolved attempts:

```text
total_booked_prints = 10 × (B + A)
prints_remaining   = total_booked_prints − C
prints_available   = total_booked_prints − C − U
```

`B` is a nonnegative whole number in Draft and must be positive at first start. Each additional entry is a positive whole package count, with a Client-request note and stable operation ID. Original booking fields freeze when Live. Additions are permitted on Live Events, including paused/finished runs before Event completion; they do not start or resume a run. Entries are immutable and cannot be silently edited or removed. Validate integer bounds at every boundary; capacity must fit the database integer type without overflow.

- `C + U ≤ total_booked_prints`; no new reservation when available is zero.
- At most one unresolved attempt system-wide; an active Guest Session is also exclusive to the active run.
- Printed consumes its held unit once; NotPrinted releases it once. Duplicate capture, package, dispatch and outcome requests never double-count.
- Five booked packages mean 50 prints. At 49 Printed plus one Pending, available is zero and the pending fault takes priority. Printed resolution exhausts all 50; NotPrinted resolution leaves one available.
- Loading a physical package changes equipment readiness only. It does not add Event capacity. Adding a purchased package changes Event capacity only. It does not prove film was physically loaded.
- Retakes and abandoned photos do not use print capacity. Each completed shutter produces one Capture; stopping before the shutter produces none. Count metadata idempotently even if the photo is discarded.

## 3. Guest journey

1. **Welcome:** silent looping montage, otherwise Event background, otherwise default. Clear Start plus short one-print/privacy copy. Start remains available while montage plays. A pause-video control and reduced-motion static fallback remain.
2. **Camera preview:** mirrored front camera, portrait Instax Mini crop, clear **Take Photo**. Background outside the preview never enters the photo.
3. **Countdown:** 3–2–1, then one shutter/Capture. Prevent duplicate shutter actions.
4. **Review:** unmirrored final crop matching the print, **Retake** and **Print**. Retake returns to live preview for another completed shutter; Print explicitly selects the newest acknowledged shutter by `captured_at`, allowing either selection at equal timestamps, independent of metadata arrival order.
5. **Printing:** after Capture metadata acknowledgement, reserve the explicitly selected eligible Capture and authorize one dispatch only while its bound Capture remains eligible under the shutter-time rule. Disable duplicate actions. Show actual preparing/sending/waiting phases without invented percentage or success on acceptance.
6. **Print complete:** only after full ejection and the server's idempotent outcome acknowledgement. Discard photo, show completion for **3 seconds**, then welcome if available. Guest does not wait for image development. If server acknowledgement is unavailable, retain non-photo evidence and show connection recovery instead of starting another session.

Capture/review inactivity expires after 90 seconds, with a warning at 75 seconds and **Continue** to reset it. Countdown and printing have no guest inactivity timeout. All fault/stop abandonment discards photo bytes immediately except bytes already being used to finish an authorized send; release those as soon as transport no longer needs them. No retry after a fault reuses the old photo.

## 4. Failure and recovery contract

### Command boundary

“Before printer involvement” means definitely no command could have reached the printer. A request that merely reserved capacity can be cancelled transactionally if dispatch never committed. Once dispatch authorization commits, assume possible delivery unless the live adapter proves not-sent. If the dispatch response is lost, query its receipt; **never send from a replayed dispatch authorization**. A crash/reload destroys permission to send that attempt. Pending reservation/dispatch state must be reconciled before any fresh guest work.

Use `POST /api/booth/print-attempts/{attemptId}/reconcile` with the valid originating device grant, a stable operation ID and reason after a fault/reload. Acquire the standard locks and inspect dispatch history. If still Reserved and dispatch never committed, **Reserved → NotPrinted**, release the hold/printer slot, end the old session and return the recorded result. A dispatch racing first instead keeps the attempt unresolved: mark Dispatching/Accepted as Pending, preserve its hold and reconcile reliable feedback or inspection. Terminal outcomes return unchanged; a Pending attempt stays Pending. No guest image or send permission is returned. If a reservation response was lost, first close the old Guest Session with its idempotent end operation under the same Event/run locks, then look up the original reservation receipt and session attempt. A reservation that committed before session end is now visible and must be reconciled; one that reaches the locks after session end is rejected. This barrier prevents a delayed request from creating an abandoned hold after recovery declared the session clear. A missing receipt alone is not proof that no reservation exists; wait for the session-end acknowledgement and resulting state before admitting a new guest. **Admin recovery uses the same unsent check** when the device proof is lost, so server-proven unsent Reserved work requires no Printed / Not printed inspection. Session end alone still never guesses a physical outcome.

Stop unsent work immediately. Cancellation of a delivered physical command is **not promised**. Let a command already being executed finish when possible, collect its result, and block new work. Never automatically resend a photo after any fault, reload or ambiguous response.

| Failure                                                                                   | Before possible delivery                                                                        | After possible delivery                                                                                                    | Recovery and guest message                                                                                                                                                                                |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bluetooth disconnect                                                                      | End session, discard photo; cancel Reserved/definitely-not-sent work                            | Keep unresolved attempt; observe if possible, otherwise Pending                                                            | **“Bluetooth disconnected. Please inform the Admin.”** One action: **Connect to Instax**. After connection, reconcile old attempt, verify printer ready and return to welcome only when all guards pass.  |
| Internet unavailable                                                                      | End session and discard photo; reconcile any lost reservation response after connection returns | Stop additional sends, retain non-photo outcome evidence; current physical print may finish; Pending if no reliable result | **“Wi-Fi disconnected. Please inform the Admin.”** for detected offline connectivity. Retry connection checks automatically; no Print retry button. Once restored, settle old attempt then fresh welcome. |
| Server error with connectivity unknown                                                    | Same as network failure                                                                         | Same as network failure                                                                                                    | **“Connection unavailable. Please inform the Admin.”** Do not diagnose Wi-Fi from an RPC timeout or HTTP error alone.                                                                                     |
| Camera permission/feed lost                                                               | End session/discard photo, stop countdown if shutter has not fired                              | Finish/resolve current print while blocking another session; then present camera recovery                                  | **“Camera disconnected. Please inform the Admin.”** with **Enable Camera**. Permission and an actual live feed must both return before welcome.                                                           |
| Page reload/crash                                                                         | Photo is lost; reconcile metadata and any Reserved operation, then welcome after readiness      | Pending unless reliable feedback establishes outcome; never re-send                                                        | Temporarily unavailable until attempt/readiness reconciled. An ordinary reload retains the valid device grant.                                                                                            |

Printer chooser dismissal, failed reconnect or camera permission denial leaves that blocker active with the same permitted action. These controls authorize only local connection/permission recovery, never Admin/accounting operations. Technical diagnostics and Printed / Not printed choices remain on the authenticated phone page.

### Reload and exceptional inspection on the phone

An outstanding reload request is bound to Event, run, printer identity and a unique `reloadRequestId`. The Admin opens `/events/[eventId]`, physically loads a package and chooses **Confirm film loaded**. The server records who confirmed, when and which request. A stale confirmation cannot clear a newer reload request or a fault from a different printer/connection generation. If a reload occurred before confirmation and caused reconnection, refresh the phone panel and confirm against the current request. Reliable automatic reload detection is optional, subject to physical proof; the manual flow is the supported fallback.

If a previous attempt is Pending, show **Printed / Not printed** plus a required inspection reason. Printed means a sheet fully ejected, regardless of quality. Not printed means inspection establishes no sheet ejected **and the old job cannot later produce output**. Mere absence of a visible sheet or the act of reloading is insufficient. If inspection cannot establish either, keep Pending and explain that the printer must be inspected/cleared safely before continuing. A later reliable adapter report may resolve the same attempt instead; concurrent resolutions serialize and cannot count twice.

Reload confirmation and outcome resolution are separate idempotent operations in the same recovery panel. Each operation has its own receipt; one succeeding does not imply the other succeeded. Known outcomes require no extra Printed / Not printed choice. No previous attempt is blanket-rejected by reloading. Confirmed Printed stays counted; known NotPrinted stays terminal; unknown stays Pending until resolved.

Before enabling new work, establish that the printer is idle/ready and that the old command cannot still execute, using a physically qualified adapter check or the qualified Admin recovery procedure. Reconnecting alone does not establish this. If neither can establish it, the booth remains unavailable. A load confirmation does not claim ten usable sheets were detected and does not trust the printer count as inventory.

### Overlapping faults and Admin stops

Track blockers independently. Clearing Bluetooth does not clear no-film, camera, connectivity, pending outcome, exhausted booking, or explicit pause. The server returns all non-sensitive blockers; the screen presents one principal status and any necessary recovery control. Priority is: Finished/invalid access; Finishing; deliberate Paused; unresolved print; connection; Bluetooth; camera; printer/reload; booked-print exhaustion; welcome. If a pending print also lacks Bluetooth, show temporary-unavailability copy with the Bluetooth message and **Connect to Instax**. During a print with only a camera fault, keep printing visible until its outcome is settled, then show camera recovery. This presentation priority never suppresses a recoverable connection/camera action needed to settle work.

**Pause Booth** records Paused immediately and displays **“Booth paused.”** On a pending print, also show truthful printing/recovery status. **Resume Booth** is authenticated on the phone and requires all readiness conditions; a failed Resume leaves Paused. **Finish Booth Mode** displays **“Finishing Booth Mode”** while an attempt remains unresolved, then **“Booth Mode finished”** with **Sign in**. The iPad does not sign in for pause/resume. There is no guest-accessible local Admin exit/pause gesture; the Admin uses the phone or, for exceptional access loss, the protected setup/sign-in path. Guided Access exit remains an OS/passcode action.

Remote stops and dispatch authorize under the same run/attempt transaction locks. A stop committed before dispatch denies dispatch and settles Reserved as NotPrinted. Dispatch committed first may still reach the printer even if the remote stop or its response arrives milliseconds later; mark the run stopped, prohibit subsequent work and wait for this outcome. The app must not promise instantaneous cancellation across devices. A client rechecks its locally known stop/fault before its one send; a late stop never revives or retries work.

### Capture ordering

[ADR-0026](../../adr/0026-order-captures-by-shutter-time.md) refines Capture eligibility. At reservation, the explicitly selected acknowledged version-2 Capture must exist in the correct Guest Session/run; reject it if another acknowledged version-2 Capture in that session has `captured_at > selected.captured_at`. At dispatch, apply the same check to the attempt's bound `capture_id`; never choose a replacement photo. Equal shutter timestamps permit either explicitly selected acknowledged Capture, regardless of metadata arrival or UUID order. Older or tied metadata arriving after reservation does not invalidate it. A genuinely newer acknowledged shutter blocks dispatch of the older bound Capture; existing reconciliation settles its proven unsent reservation as NotPrinted without a physical send. Every acknowledged Capture counts once. Preserve timestamp validation and the bounded late-Capture exception below; add no sequence field or selection endpoint.

### Transactions and invariants

Accounting writes go through private database functions invoked by trusted server handlers. Functions recheck actor scope, current session/grant validity, Event/run state, revision and receipt payload inside the transaction. Use a fixed search path, explicit grants and a dedicated restricted execution boundary; never grant `anon` or ordinary `authenticated` clients direct execution of accounting functions or table writes that bypass them. Admin RLS remains for reads, Profile edits and validated Draft edits. Direct Draft writes cannot alter lifecycle, counters, package additions, grants or accounting version.

Lock order: global single-printer/single-Live-Event guard → Event → run → attempt or reload request. All functions touching those resources follow the same order. Uniqueness constraints provide a final guard against multiple Live Events, unfinished runs, active guest sessions or unresolved printer attempts. Reservation, derived counts, audit entry and operation receipt commit atomically. There is no database transaction across a Bluetooth write.

All mutations use a stable `operationId` plus normalized payload fingerprint. Repeating the same actor-scoped key and payload returns the existing result after fresh authorization; changing payload with the same key returns `409 operation_conflict`. Retain receipts with Event history. A timeout/503 may be a committed operation: recover its receipt, never generate a new key for an uncertain package addition, outcome or start. Replayed dispatch authorization returns status only, never permission for another physical send.

Persist a metadata-only journal before reservation and before any physical write, binding operation, attempt, run and connection generation. The adapter has a one-send barrier. Journal/storage failure prevents dispatch. Journal loss after dispatch means Pending and requires reconciliation; it is not evidence of no send. Never persist photo bytes, encoded image payload, grant secrets or Client contact in this journal. Remove acknowledged local metadata when no longer needed; retain database audit history.

### Authority and grant lifecycle

Admin handlers require the provisioned Admin and a live Auth session, including rejection of revoked-but-unexpired JWTs. Booth handlers use only the hashed, run-scoped grant in a Secure/HttpOnly/SameSite cookie, with same-origin/CSRF checks and private no-store responses. Server-only credentials never reach the browser. Client contact, global history, package additions, reload confirmation, inspection, pause/resume/finish and Event completion remain Admin-only. A booth may read sanitized run state/media and submit scoped session/capture/print observations; it never queries Supabase tables directly.

Handoff: validate `setupReady`, create Prepared run/inactive grant; sign Admin out locally on the iPad; clear its Admin cookies; issue inactive booth cookie; exchange a single-use short-lived handoff reference and confirm browser receipt; activate grant. Other-device Admin sessions survive. Failed handoff revokes the inactive grant and leaves Paused; authenticated local setup can issue a replacement after old work is reconciled. The opaque URL reference must be removed immediately and never logged.

**Same-run access recovery:** when a handoff fails or a device grant is missing/expired/revoked, the Admin signs in on the setup iPad and calls `/api/admin/events/{eventId}/booth/recover-access` for that unfinished run. This is distinct from starting a new run. Under the normal locks, end its old guest interaction and cancel a Reserved attempt only if dispatch never committed. If a command may have reached the printer, refuse replacement with `print_pending` until phone recovery establishes its outcome. Then revoke all prior run grants/handoffs, set/keep the run Paused, and issue one inactive replacement grant and single-use handoff with `purpose=recovery`. It uses the same local Admin sign-out and browser-receipt boundary. Successful receipt activates the **grant only**; the run **remains Paused**, including after an initial failed handoff. The Admin explicitly chooses Resume on the phone once readiness passes. Replacement can establish limited Paused access even when equipment/capacity is blocked; it cannot dispatch or clear those blockers. **Finishing and Finished reject access replacement**; the phone settles/finishes that run, and any later run needs a new start. Replaying the same recovery operation returns its original receipt/state, never another grant; an expired handoff needs a new authenticated recovery operation. Replayed handoff confirmation is idempotent and cannot clear an intervening pause/finish.

The device grant survives recoverable faults and Paused. Paused/Finishing grants permit sanitized state, metadata reconciliation and pending observation, but no new guest sessions, reservations or dispatch. Finish, Event terminal transition or explicit security revocation ends the grant. A Finished screen contains no Event/contact data and may be shown without a live grant. Password reset affects Admin sessions, not an otherwise-valid device grant, and never resumes a paused run.

Expiry policy: inactive handoff expires after 5 minutes. An active grant has a 24-hour idle expiry, renewed server-side when the valid device polls state or submits an authorized request while its run remains unfinished; renewal does not widen its scope. An expired/revoked/missing grant cannot renew itself. It shows **“Booth access ended. Please inform the Admin.”** with Sign in for a new local setup, after resolving any old attempt from the phone. This exceptional security recovery may require leaving Guided Access; routine faults do not. Grant possession cannot impersonate Admin inspection. While grant authority is lost, a current Admin may still inspect and resolve the identified Pending attempt from the phone.

The booth polls sanitized state every 2 seconds while visible, immediately on reconnect/focus and before Start/Print; push notifications may optimize this later. A failed poll makes server reachability a blocker. A dispatch authorization can race with a stop as described above; polling is not an instantaneous remote kill switch.

### Photo privacy and terminal metadata

Photos exist only in browser memory and direct printer transport. No server, Supabase, local/session storage, IndexedDB, logs, telemetry or history receives Guest photo bytes. Event Media is the only stored imagery; it is private, validated and served by short-lived URLs. Activity references Event IDs rather than copying Client contact.

Every shutter first journals a stable Capture operation and timestamp. Ordinary paused/fault recovery can acknowledge its metadata with the valid device grant without reopening interaction. A completed shutter racing a Finished/revoked run may submit only that Capture metadata within two minutes of stop using the original, otherwise-unexpired proof and matching just-ended session. This narrow exception cannot read state, renew a grant, reserve, dispatch, or report print outcomes. No new Capture after the stop is accepted. If the journal cannot establish that boundary, do not invent a Capture. Event totals include accepted completed-shutter records; the exception preserves the earlier implementation's bounded metadata reconciliation rule.

## 6. Endpoint shapes (target, not existing API promises)

All listed mutations are `POST`, JSON, same-origin, with `operationId`; IDs are opaque. Requests never carry photos. Responses include the operation receipt, sanitized result and state revision. Authenticated Admin reads may contain Event/Client details; booth responses never do. Existing transport names may be mapped during implementation only if these semantics and authorization remain explicit.

Read endpoints: `GET /api/booth/state` returns run state, blockers, pending attempt ID, safe recovery actions and package availability; `GET /api/booth/operations/{operationId}` returns only this grant/run's receipts. `GET /api/admin/events/{eventId}/operations/{operationId}` and the authenticated Event page expose relevant Admin receipts, pending attempts and reload requests. Use the stage-specific predicates above; dynamic readiness reports must be current at dispatch and for the same connection generation. A first start never uses a prior run's physical confirmations. Routine successful readiness heartbeats update observation freshness without incrementing the lifecycle revision; actual blocker/generation/lifecycle changes increment the state revision. The authenticated phone Event page refreshes its state every two seconds while visible, displaying Film reload needed for that Event; no out-of-app push delivery is implied.

Standard errors: `400 invalid_input`; `401 access_required`; `403 operation_forbidden` or `qualification_required`; `409 stale_revision`, `operation_conflict`, `not_ready`, `print_pending`, `booked_prints_exhausted`, `invalid_transition`; `503 operation_unavailable` for ambiguous infrastructure failures. Stable error codes plus concise safe messages; never leak credential, Client or raw device data. A 503 does not prove rollback. State/receipt recovery is allowed even when the run is Paused/Finishing; it does not grant dispatch.

## 7. Provisional printer adapter

Capabilities: connect, read safe status, observe readiness, send once for an authorized attempt, report command acceptance, report qualified full ejection, report qualified no-output rejection, report disconnect/ambiguous outcome. Cancellation after possible delivery is unsupported unless separately qualified. Simulator can emit each transition deterministically; it cannot enable production or supply physical proof.

Observations distinguish `definitely_not_sent`, `command_accepted`, `full_ejection_confirmed`, `no_film_rejected`, `outcome_unknown`, `connection_changed`, `ready_for_new_job`. Include attempt correlation and adapter/evidence-policy version. A generic status packet is not automatically any of these outcomes. Connection changes invalidate dynamic printer readiness; querying a counter after reconnection does not resolve an old attempt. Cross-connection full-ejection correlation must be proven, or use Pending and exceptional inspection.

The server's release policy must reject simulated evidence in production and physical ejection assertions from an unqualified adapter. Once qualified and enabled, allow inspected Printed/Not printed only for exceptional Pending recovery under Admin authority; this must not become the normal success path. The detailed fault, no-film, idle/ready and safe clearing procedures must pass their checklist cases before real guests use them. A missing capability has an explicit unavailable/manual-recovery fallback; a missing automatic normal-ejection capability keeps real Booth Mode disabled.

## 9. Acceptance for later implementation

- Formulas and last-print concurrency preserve capacity; duplicates and lost responses cannot add packages or count twice.
- A new guest never starts while an old attempt might still eject; no reconnect/reload automatically sends the old image.
- Happy flow includes review, Retake and 3-second completion; failures discard old guest photos.
- Bluetooth has one Connect to Instax action; camera has Enable Camera. Neither requires routine Admin sign-in.
- Phone load confirmation and optional exceptional inspection work independently; pause survives every recovery.
- Finish Booth and Complete Event are separate; terminal history is retained; Draft deletion remains safe.
- Access/RLS/CSRF, revoked sessions, idle expiry, handoff failure, journal loss, cross-device stop/dispatch races and stale reload requests are verified.
- The [physical proof checklist](../../qualification/booth-recovery-proof-checklist.md) passes automatic normal completion and actual-iPad release gates. No manual-per-print substitute is accepted.
