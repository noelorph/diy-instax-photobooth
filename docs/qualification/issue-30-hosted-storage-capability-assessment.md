Enabling that protocol does not select the physical storage backend. Supabase documents those as [independent features](https://supabase.com/docs/guides/self-hosting/self-hosted-s3).
- The same file contains experimental `env(S3_HOST)`, region and credential references. These placeholders do not identify a provisioned production bucket, provider, region or self-hosted deployment. No production self-hosting configuration was found in the scoped repository search.
- `src/lib/supabase/server.ts` takes the Supabase URL and publishable key from environment configuration. `tests/fixtures/local-supabase.ts` explicitly requires the local API on port 56321. Neither establishes the hosted Storage version or physical bucket configuration.
- The [saved qualification](issue-30-isolated-multipart-proof.md) used Storage v1.79.36 with its **file backend** and disabled queue. It is not a hosted-backend qualification.

Therefore evaluate the **managed Supabase customer API/support boundary**, not direct access to an AWS bucket or a locally mounted volume. The production project identity, region, deployed Storage build, underlying provider, lifecycle configuration and support entitlement remain unverified. No hosted project inspection or credential read was needed for this intended-target determination.

## Supported recovery options found

| Option                                            | Evidence and limitation for our contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public multipart APIs                             | [S3 compatibility](https://supabase.com/docs/guides/storage/s3/compatibility) lists ListMultipartUploads, ListParts and AbortMultipartUpload. These are useful for tracked sessions. The pinned implementation lists database session rows and requires a row before Abort reaches its backend. Documentation does not establish discovery/recovery when creation fails before that row persists.                                                                                                                                                                                                                                            |
| Provider automatic abort                          | [S3 upload documentation](https://supabase.com/docs/guides/storage/uploads/s3-uploads) says multipart uploads are automatically aborted after 24 hours. It does not specify whether backend-only sessions are included, how concurrent requests are drained, the physical removal deadline, retry behavior after cleanup failures, or a customer-visible acknowledgment. Treat this as a documented recovery mechanism to clarify with the vendor, not a verified deletion receipt.                                                                                                                                                          |
| Storage API removal / Studio / S3 object deletion | [Delete Objects](https://supabase.com/docs/guides/storage/management/delete-objects) prescribes the Storage API. Its bulk-emptying guidance concerns listed objects; it does not establish discovery of pre-existing unlisted staging sessions. The [schema guide](https://supabase.com/docs/guides/storage/schema/design) distinguishes metadata from underlying bytes and warns against manipulating Storage rows. Do not manufacture a missing session row or delete metadata as a repair.                                                                                                                                                |
| Hosted orphan cleanup through Support             | Supabase's [March 2026 reliability announcement](https://supabase.com/blog/supabase-storage-performance-security-reliability-updates) confirms an orphan scanner exists. A [reply in Supabase's discussion #34254](https://github.com/orgs/supabase/discussions/34254) describes Support scanning, sharing results and removing approved orphans. This is a recovery avenue to request, not a documented automated per-Event completion contract. The reply concerns orphaned objects after SQL deletion, not failed multipart creation. Ask specifically about incomplete uploads, staging metadata, authorization and completion evidence. |
| Bucket lifecycle configuration                    | The current [updateBucketLifecycle reference](https://supabase.com/docs/reference/javascript/file-buckets-updatebucketlifecycle) supports only noncurrent-version expiration and is feature gated. It does not offer incomplete-multipart abort. The S3 compatibility page still marks S3 lifecycle configuration unsupported; do not generalize that into “no lifecycle APIs exist.” The narrower current API also does not close this gap.                                                                                                                                                                                                 |
| TUS URL expiration                                | [Resumable upload documentation](https://supabase.com/docs/guides/storage/uploads/resumable-uploads) documents upload URLs valid for up to 24 hours. URL expiry is not a complete transfer inventory, physical cleanup acknowledgment or drain guarantee. Current application TUS behavior remains unchanged.                                                                                                                                                                                                                                                                                                                                |

Supabase's [S3 credentials](https://supabase.com/docs/guides/storage/s3/authentication) address its project endpoint. They are not evidence of customer access to the underlying provider bucket or its lifecycle controls. The supported self-hosted S3 configuration is a different deployment model, not an established option within this project's managed deployment.
