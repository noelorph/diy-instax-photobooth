## Implemented diagnostic rules

Only the development qualification harness changes. The transport framing, image transfer, single-send print controller, manual physical confirmation, local three-sheet allowance, Booth adapter, server accounting and reload authority remain outside this prototype's changes. The page remains development-only.

| Candidate | Required observations                                                                                                                                                                                                                                                    | Exclusions                                                                                                                                                                                                                                                                           |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Ejection  | After an accepted print, status selector 2 shows operation active, operation-info 1 and result 127, then idle, operation-info 0 and result 0.                                                                                                                            | Initial idle or count change alone is insufficient. Cover open, error flag/code, invalid battery, reserved status bit, unknown operation/result, malformed response or observation error invalidates the candidate. Final reported film may be zero.                                 |
| Reload    | Closed, inactive status and history selector 3 establish a baseline; observe cover open then closed; a subsequent history response has exactly +1 `totalEjectFCNum`, unchanged `totalPrintNum`, and the latest status is closed/idle/normal with positive reported film. | Missing baseline/open/closure, counter reset/decrease/wrap/jump, print-counter change, another cover cycle, error or interrupted observation invalidates the candidate. The November 7 trial supports the FC/cover association; exclusivity under other conditions remains unproven. |

Both decode successful opcode `0x0002` replies with the recovered ten-byte payload layout. Unknown layouts are retained as raw evidence and rejected for candidates. Ejection polls selector 2 every 900 ms; reload serially polls selectors 2 and 3 on that interval, skipping ticks while a query is pending. Each observation lasts at most 60 seconds. This is the existing harness sampling cadence, distinct from the official app's recovered one-second delay.

Each observation has its own ID and connection generation; ejection observations also carry the current print-attempt ID. Cancellation ignores late replies. Reconnect requires a new observation and baseline. Page hiding, transport/query failure and disconnect invalidate the observation. Candidates are timestamped once and never invoke physical confirmation, replenish film allowance, resolve an uncertain print or permit another print. Later invalidation remains visible and logged even if a candidate was previously observed.

Connecting with zero reported film is now allowed for diagnostics. The print path still rejects zero film before image transfer or print dispatch. Starting reload observation disables print readiness; stop and reconnect to check readiness afterward. This deliberate check does not establish that reported film equals usable inventory.

## Physical test together

Use the existing trusted HTTPS development setup and Bluefy on the intended test device. Record printer model, firmware, browser/device version, source revision, test case, actual loaded contents and outcome beside each exported log. The harness logs model/firmware in its connection metadata. Film use and physical manipulation remain supervised.

1. For ejection, use the existing camera → capture/review → one Print workflow. Keep the full exit path and the page's UTC clock in synchronized video. Observe the candidate label without treating it as confirmation. Tap **Sheet fully emerged** only when the entire sheet is out, retain the existing ten-second status tail, then tap **Observed film ejection**. Export the non-photo JSON before starting another test. Include normal fresh prints and a last-sheet print.
2. For reload, connect in setup; camera permission is unnecessary. Start **Observe reload** with the cover closed. Wait for **Baseline captured** before opening anything. Record one controlled load/cover cycle. Tap **Reload cover fully emerged** at complete dark-cover exit when applicable. Leave observation running through settled status/history, then stop and export the log. If baseline cannot be read or time expires, record that result and restart with the cover closed; do not infer the missing sequence.
3. Compare a permitted fresh pack against safe, deliberately prepared negative cases: cover-only cycle, empty cartridge, partial/used contents, and reconnect/power-cycle boundaries. Do not open a loaded fresh pack just to create a negative case. Existing uncertain print outcomes must be reconciled independently before reload probing; the reload button does not clear them.
4. Compare `ejection-candidate` and `reload-candidate` UTC/elapsed timestamps with video frames and `physical-ejection-marker` / `physical-reload-cover-emerged`. Keep `status`, `print-history`, `candidate-invalid`, start/stop and disconnect events. A human tap has reaction delay; a candidate preceding the tap does not by itself prove it preceded physical exit.

Reject the ejection rule as physical authority if it can fire before full exit or after partial/jammed output. Reject the reload rule as automatic load authority if invalid loads yield the same sequence, or if it cannot distinguish an outstanding old print. A positive film count and FC increment do not prove ten usable sheets. These results determine whether automatic reload detection is feasible with this protocol; they cannot be manufactured by adding a timeout or assuming the counter name proves its meaning.

Physical acceptance still follows the [proof checklist](../../booth-recovery-proof-checklist.md), [dated issue #17 report](../../issue-17-trial-report.md), and [replacement contract](../../../superpowers/specs/2026-10-21-package-accounting-booth-recovery-design.md). The linked physical reports record accepted detection milestones; production authority and the actual iPad release gate remain separate.

## Software verification

Focused qualification tests cover the decoded historical bytes, last-sheet completion candidate, invalid/missing sequences, negative reload cases, counter changes, serialized queries, deadline/cancellation, stale callbacks, correlation, and isolation from allowance/manual confirmation. Browser checks use a synthetic Bluetooth device and do not count as physical evidence.

Commands: `npx --no-install vitest run src/features/qualification`, `npx --no-install tsc --noEmit --incremental false`, and `npx --no-install eslint src/features/qualification`.

2026-11-06 local results: 96 tests passed across all eight qualification test files; TypeScript, focused ESLint and changed-code formatting checks passed. All 26 raw record checksums and relative evidence links verified. A Chromium run through the real page and transport using synthetic GATT replies reached both candidates, kept physical confirmation mandatory, sent exactly one print command for the print flow and no print/transfer commands for reload, and exported correlated logs. Reload layouts had no horizontal overflow at 390×844, 820×1180, 1440×1024, 844×390, or 390×844 with 200% text size. Phone reload and tablet print screenshots were visually inspected. Physical printer, Bluefy and actual iPad checks were unperformed at this software-verification checkpoint; later physical observations are linked above. No production build or unrelated integration suite was run for that checkpoint.
