## Findings

### 1. Narrow the expiry claim to the observation retained (reporting, medium)

`docs/qualification/issue-30-isolated-multipart-proof.md:45` includes expiry among passed capability restrictions. `docs/qualification/multipart-isolated/proof.mjs:123` accepts any response status at least 400 after waiting 3.1 seconds; it discards the body. Both final logs at line 18 record `expired-part` as HTTP 400 without an API error code. This is evidence that a request using the previously usable part capability was rejected after its two-second validity window; it does not independently establish an expiry-specific authorization error rather than another request/server error. The binding mutations do retain HTTP 403, and the alternate-API assertions at `proof.mjs:122` require authorization status explicitly, so those observations are stronger.

Suggested reporting-only correction: say “a request using the same part capability was rejected after its expiry window (HTTP 400; expiry-specific error reason not retained).” Preserve the exact-run harness and evidence. Do not rerun or weaken an assertion to address this documentation limit.

### 2. Exact names alone do not establish volume/network ownership (latent recipe safety issue, medium)

`docs/qualification/multipart-isolated/runtime.mjs:55` checks the ownership label before removing containers. Lines 60–61 remove matching volume/network names without checking labels or tracking whether this invocation successfully created them. Startup checks only for existing resources carrying the qualification label (lines 24–25), and `proof.mjs:154` calls teardown even when startup throws. A future invocation that encounters a pre-existing unlabeled resource with an exact proof name could therefore remove it during failure cleanup; a matching network can trigger the failure at startup and then be removed in `finally`.

This does **not** establish a problem in the saved runs: their runtime records show the dedicated resources, completed teardown records exist, and the controller supplied a subsequent exact-resource absence audit. It does mean README line 33's reusable recipe claim “only exact owned” is stronger than the volume/network guards. Record this limitation for any independently authorized future recipe revision; no fix or execution is part of this stopped review.

### 3. Make the synthetic padding limit visible beside the size result (reporting, low)

`docs/qualification/issue-30-isolated-multipart-proof.md:41` accurately reports transferred byte counts and validator acceptance, but does not explain that `proof.mjs:21` pads a 2×2 PNG with a tEXt chunk and a tiny 32×32, 1 fps video with an MP4 `free` box (`proof.mjs:85`, `proof.mjs:86`; `tests/fixtures/event-media/README.md:11`). The saved 10,000,000/50,000,000-byte results establish transport size, byte identity and this validator's acceptance. They do not establish decoding a comparably large real image/video workload or iPad playback. Video validation parses sample configuration/extents/timing rather than decoding H.264 pixels (`tests/fixtures/event-media/README.md:30`). Add a short fixture limitation to the report; no new fixture or runtime work is needed.
