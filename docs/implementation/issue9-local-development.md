## Local development

Install dependencies with `npm ci`, configure local Auth as described below, then run `npm run dev` and open `http://localhost:3000`. For local HTTPS device testing, place your certificate key at `certificates/booth-key.pem` and certificate at `certificates/booth.pem`, then run `npm run dev:https`. Open `https://localhost:3000` on the development computer or use the network URL printed by Next.js on the test device. The certificate must be trusted by the device and valid for the address used. The `certificates/` directory is ignored by Git; do not commit private keys. See [ADR-0013](../../docs/adr/0013-use-optional-https-for-local-device-testing.md). Available checks include `npm run lint`, `npm run format:check`, and `npm test`. Admin authentication, Profile, responsive navigation, Event management operations, Film Stock, Additional Prints, Test inspection, uncertainty resolution, Wasted Film, Client Redaction, Draft deletion, and History are implemented locally. `/events/[eventId]` manages the Event; `/booth` runs the nonproduction simulated Guest flow and protected Admin return. Dashboard remains a foundation surface. Physical printer operations remain gated; final combined verification is tracked separately. See the [Booth guide](../../docs/booth-user-flow.md).

Reusable UI lives in `src/components/{ui,shared,layout}` under [ADR-0020](../../docs/adr/0020-place-shared-ui-components-under-src.md). The ordinary `@/*` → `./src/*` mapping resolves `@/components/...`; `components.json` uses the same aliases for shadcn additions. Feature state remains in `src/features/admin/`.

### Local Auth and database

With Docker running, run `npx supabase start`. This checkout uses the isolated `diy-instax-admin` project: API at `http://127.0.0.1:55321`, database on port `55322`, Studio at `http://127.0.0.1:55323`, and the Mailpit test inbox at `http://127.0.0.1:55324`. The pinned CLI applies the versioned migrations when starting a fresh stack. After adding a migration, use `npx supabase migration up --local`.

Run the Auth/Data API checks with `npm test -- tests/integration/admin-authorization.test.ts`. The fixtures discover only this local stack, reject any other API address, create temporary Auth users through its Admin API, allowlist only each test's Admin, and clean up the users and their Profiles/sessions. They never read application environment credentials. `npm test` includes these integration tests and therefore needs this local stack running. Vitest serializes test files because they share the local Auth/database stack and assert complete Draft lists; run Vitest and Playwright separately against it. Inspect local database security with `npx supabase db advisors --local`.

Public registration is disabled by `[auth].enable_signup = false`. Keep `[auth.email].enable_signup = true`: that setting enables the email provider, including existing-user login. Approved local recovery callback URLs are listed explicitly in `supabase/config.toml`; production must configure its own exact application callback URL and SMTP delivery.

In an ignored `.env.local`, set `NEXT_PUBLIC_SUPABASE_URL` to the local API URL and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to its publishable/anon key from `npx supabase status`. Set server-only `SUPABASE_SECRET_KEY` to the local privileged key from the local stack; never use a `NEXT_PUBLIC_` prefix or expose it to the browser. Opt in to simulated operations with server-only `BOOTH_SIMULATOR_ENABLED=true` outside production; production refuses this simulator even when the flag is set. Set the server-only `ADMIN_AUTH_ORIGIN` to the application origin used in the browser, such as `http://localhost:3000` or `http://127.0.0.1:3000`. This validated origin is also the canonical same-origin comparison for operation requests; configure the exact browser origin, including port. Origins must have no credentials, non-root path, query, or fragment; invalid configured values fail closed. Cross-site operation requests are refused. Recovery always sends the configured origin's `/auth/callback` URL; headers and form fields cannot choose it. The corresponding exact callback URL must also be approved in Supabase Auth settings. Missing or invalid origin configuration produces neutral retry feedback. Production origins require HTTPS; only `localhost` and `127.0.0.1` may use HTTP. Recovery emails arrive in local Mailpit. Open the link in the same browser that requested it so the PKCE verifier is available. The fixed callback exchanges the single-use code and opens the public reset form; invalid, expired, or reused links offer another recovery request.

Run focused public form/action and Mailpit checks with `npm test -- tests/components/admin-auth.test.tsx tests/integration/admin-auth-actions.test.ts`. Sign-in checks the provisioned Profile through live-session RLS before opening `/dashboard`; a valid non-Admin login is denied and signed out locally. Wrong passwords and unknown addresses receive neutral feedback. Forms preserve the entered email, retain actionable errors, and block submissions while pending. Recovery gives the same confirmation and retry path for known and unknown addresses, including account-dependent cooldown or delivery errors. Confirmation does not guarantee delivery. Only address-independent configuration or connection failures show generic retry feedback.

### One-time Admin provisioning

For each environment, an authorized project owner provisions the sole Admin in two steps:

1. Create the email/password Auth user through the Supabase Dashboard's **Authentication → Users** interface or the server-only Auth Admin API, with an appropriately verified/confirmed email. Copy its user ID. Do not insert directly into `auth.users`.
2. Through the Dashboard SQL editor or another trusted admin-only database operation, insert that ID into `public.admin_profiles`:

   ```sql
   insert into public.admin_profiles (id, phone, theme)
   values ('<copied-auth-user-id>'::uuid, null, 'light');
   ```

Keep public signup disabled in production Auth settings while keeping email login enabled. Provision only the owner; another Auth user is not an Admin unless a trusted operation explicitly adds its Profile. There is no browser provisioning endpoint, and authenticated clients cannot insert/delete Profiles or change their IDs. They may update only phone and the `light`/`dark` theme.

`private.is_active_admin()` checks the current Auth user, its allowlisted Profile, and the JWT's session ID against `auth.sessions`. Profile RLS uses this predicate on reads and updates so original, unexpired JWTs lose data access after their session is revoked. The private schema is not exposed by the Data API; the function has a fixed empty search path and only the authenticated execution grant needed by RLS. Later Admin data policies must reuse this predicate. Hosted promotion remains pending until the owner identifies a separate staging Supabase project; the connected hosted project has not been confirmed as staging or production. Apply and verify migrations in the identified staging project before production through the documented deployment process. The implementation and checks described here use only the isolated local stack and do not configure or modify a hosted project.

Password reset requires an Auth-verified recovery session and an active provisioned Admin Profile. It saves a matching 12–128 character password that differs from the current one, globally signs out all Admin sessions (including recovery), and offers fresh sign-in only after both steps are confirmed. Existing JWTs immediately lose protected data access through the live-session RLS predicate after revocation. Reusing the current password shows a field error and does not end sessions or report success. If the revocation response fails after a successful save, the form says the reset is incomplete. A confirmed-active recovery session may submit another different password to retry; a revoked or unverifiable recovery session is directed to request a new recovery link, with no claim that all sessions ended. See [ADR-0015](../../docs/adr/0015-complete-admin-reset-only-after-password-change-and-revocation.md). Run `npm test -- tests/integration/password-reset.test.ts tests/components/password-reset.test.tsx` for the local Mailpit journey, expired/reused link checks, and two-session revocation proof.

### Profile and browser verification

Profile shows the verified Admin email and saves an optional phone number and light/dark preference through active-session RLS. Authenticated password changes require matching 12–128 character values. The local Auth provider was observed to end other existing Admin sessions after a password change. Profile Sign out revokes only the current device; other Admin sessions remain active. Failed operations retain feedback and permit retry; an uncertain sign-out result is never presented as success. Expired or revoked protected access returns to sign-in with persistent, neutral sign-in-again feedback. The shared shell keeps Profile last, with a phone menu, collapsible tablet rail, and wide sidebar. The [Admin UI refresh](../../docs/superpowers/specs/2026-10-15-admin-ui-refresh-design.md) uses locally served Geist Sans across Admin and future Booth Mode under [ADR-0019](../../docs/adr/0019-use-geist-typography-across-admin-and-booth.md).

Run `npm test -- tests/components/admin-shell-profile.test.tsx tests/integration/admin-profile.test.ts` for focused checks. Install the browser with `npx playwright install chromium`, then run `npm run test:e2e`. Playwright starts a production build on port 1437 against the isolated local stack and checks keyboard navigation, theme/phone persistence, password change, local sign-out, another active device, and Draft create/list/view/edit journeys. Native Chromium 200% page zoom is exercised through a test-only extension using `chrome.tabs.setZoom(2)`: tests verify the viewport halves from 1000/1440/2400 to 500/720/1200 CSS pixels, device pixel ratio doubles, and responsive media queries select the compact/medium/wide layouts. They exercise navigation, Profile, Draft forms/list, validation, and keyboard access at that zoom, and save viewport screenshots and metrics under ignored `test-results/`. Separate CSS scaling checks remain supplemental. Tests create and remove temporary Auth and Event fixtures. Run `npm run lint`, `npx tsc --noEmit`, `npm test`, and the browser suite separately; the production build does not run lint.

These earlier Admin checks do not qualify physical printing. ### Draft Event verification

`/events` lists current Events, `/events/new` creates Draft bookings, and `/events/[eventId]` edits Draft details and presents state-appropriate operational controls. `/history` lists Completed and Cancelled Events. Saves validate contact fields, whole nonnegative counts, and venue-local schedules; package count and Print Allowance stay independent. IANA names are normalized before persistence, and a zone rejected by the database returns a time-zone field error. DST gaps/overlaps and stale revisions cannot silently change a booking. Each Event retains its own Client snapshot, with active-session Admin RLS on reads and writes.

Run `npm test -- tests/unit/draft-event.schema.test.ts tests/integration/draft-events-dal.test.ts tests/integration/draft-events-rls.test.ts tests/components/draft-event-ui.test.tsx` for focused validation, persistence, authorization, concurrency, and form-state checks. Fresh full verification uses `npm test`, `npm run test:e2e`, `npx tsc --noEmit`, `npm run lint`, `npm run build`, and `git diff --check`. Issue #9 adds Draft deletion, Live transitions, Booth grants, simulated readiness/Test Prints, stock and reservation accounting, Additional Prints, Client Redaction, and operational History. Optional Event Media upload/presentation is not established by this slice; deletion/redaction includes a retryable media-removal boundary. Simulated accounting does not enable physical printer-backed Confirmed Prints.
