# Printing qualification milestone — historical prompt

> **Historical input, not an active work order or product specification.** This prompt raised the question of how to begin development before the first-release iPad A16 was available. The current answer is recorded in [ADR-0014](../adr/0014-move-print-qualification-to-integration-checkpoint.md), the [PRD](../../PRD.md#3-development-and-launch-feasibility-gates), [architecture](../../ARCHITECTURE.md#8-verification-and-delivery), and [design system](../../DESIGN_SYSTEM.md#1-authority-and-scope). ADR-0012 preserves the earlier decision and is superseded on development timing. Follow ADR-0014 and the current GitHub issues if any wording here differs.

## Original question and evidence

The owner could test with an iPhone 15 Plus and Instax Mini Link 3 but did not yet have the first-release iPad A16. The question was whether an iPhone trial could justify building the full Admin and print-accounting system, with a separate iPad trial before launch.

The owner reported Bluefy 3.9.3 and Mini Link 3 firmware 0102(RX). Device, browser, and firmware versions must be verified again during each physical trial. Earlier work in [another photo-booth project](https://github.com/noelorph/diy-souvenir-spot-photobooth) and its [printer session code](https://github.com/noelorph/diy-souvenir-spot-photobooth/blob/95990570b013a37aefb127f9a8ec64a90bbfab7f/src/lib/instax/instax-print-session.ts) offers a protocol hypothesis: a 600 × 800 baseline JPEG upload, an acknowledged `PRINT_IMAGE` command, and a Film Remaining change were observed in a MacBook Chrome run. That evidence does **not** prove correct physical output, reliable film ejection, or iPad support. Use it only as a reference for an isolated trial; do not copy that project's Guest flow or photo-retention behavior.

## Agreed resolution

1. **Physical completion checkpoint — [issue #17](https://github.com/noelorph/diy-instax-photobooth/issues/17).** The iPhone qualification harness and trial produced useful evidence, but did not establish reliable full-ejection feedback. Continue investigating automatic detection. Before printer-backed Booth Mode, Test Prints, stock consumption, or Confirmed Print accounting are completed or enabled, choose and physically validate an ejection-confirmation approach. A supervised/manual approach requires a separate explicit production design and validation. Qualification sheets are recorded manually, outside Event accounting.
2. **Integrated development.** Under ADR-0014, Admin and Booth development may proceed with a simulated printer and provisional outcome contract while #17 remains open. Keep command acceptance, physical confirmation, clear pre-film rejection, and uncertainty distinct. Do not auto-confirm or automatically resend an ambiguous attempt. The Admin foundation in [issue #14](https://github.com/noelorph/diy-instax-photobooth/issues/14) has been implemented on `development`; its issue remains open until this worktree's documentation changes are merged.
3. **Open product decisions — [issue #8](https://github.com/noelorph/diy-instax-photobooth/issues/8).** Decide how remote Admin interruption affects an active Guest Session, how an Admin can retry a selected photo after a clear pre-film rejection while sign-in and photo-discard rules apply, and whether a Draft Event with operational records can be deleted. These decisions are prerequisites for the affected accounting and access contracts in [issue #9](https://github.com/noelorph/diy-instax-photobooth/issues/9); they do not reinstate the superseded iPhone development gate.
4. **Integrated milestone and iPad launch gate.** Build and verify the integrated Admin and Booth flows in [issue #10](https://github.com/noelorph/diy-instax-photobooth/issues/10) after its affected contracts are defined. The actual iPad A16 trial in [issue #7](https://github.com/noelorph/diy-instax-photobooth/issues/7) remains mandatory before first-release deployment. iPhone evidence and simulation do not establish iPad support or make an iPhone a supported booth.

The original request was for analysis and a plan before changing implementation files. The later PRD, ADR, and milestone issues now govern the implementation sequence.
